CONFLICT (content): a merge conflict

Two commits changed the same lines of the same file, and Git won't guess which is right. The pull stops, leaves both versions in the file, and waits for you. 

%CAPTURE:pull-conflict-merge%

What Git checked

A pull first fetches (main -> origin/main: the remote's main moved), then joins the new commit with yours. Auto-merging api.py says Git tried: it took the version both commits started from, bot's version and yours, and merged them line by line. Where only one side changed a line, that side wins silently. Where both changed the same line there is no rule, so Git reports CONFLICT (content) and the file, and the merge stops: Automatic merge failed; fix conflicts and then commit the result.

The file now holds both sides between markers, and git diff shows them: between <<<<<<< HEAD and ======= your side, between ======= and >>>>>>> theirs, the commit being merged in. Lines Git could settle on its own sit outside the markers.

What to do now

Edit the file until it says what it should, markers gone. git add it, which tells Git the conflict is resolved, and git commit to finish the merge; with no message of your own, Git's (Merge branch 'main' of …) does. The merge commit has two parents, bot's commit and yours, and your main now holds both. To get out instead, git merge --abort puts everything back as it was before the pull.

The same conflict under a rebase

%CAPTURE:pull-conflict-rebase%

pull --rebase doesn't merge; it takes your commit off and replays it on top of bot's. The replay hits the same clash, prints the same CONFLICT line, and adds error: could not apply …: the commit it was replaying. git status says where you are: rebasing main onto bot's commit, with api.py both modified. Resolve the file, git add it, and git rebase --continue; Git finishes the replay and prints Successfully rebased and updated refs/heads/main. There is no merge commit, only your commit, rewritten on top. git rebase --abort is the way back.

Letting one side win: -X ours, -X theirs

When one side should simply win, a strategy option settles every clash without stopping: -X ours keeps one side, -X theirs the other, and only for the lines that clashed. Under a merge, ours is your branch. Under a rebase the names swap: the branch you're replaying onto, bot's main, is ours, and the commit being replayed, yours, is theirs. So during pull --rebase, -X ours keeps bot's line and -X theirs keeps yours: 

%CAPTURE:pull-rebase-ours%

With -X ours, bot's version wins the clash and nothing of your commit is left to apply, so Git drops it (patch contents already upstream) and your main is bot's. 

%CAPTURE:pull-rebase-theirs%

With -X theirs, your commit lands on top with your line, and git diff origin/main shows the one line that differs: bot's replaced by yours. Bot's commit is still in the history; its change to that line is not in the file.

Why the game does this to you

In %BRAND% a commit is a card, and a conflict is a pull that brings in a commit touching the same file as one of your unpushed commits. Nobody is there to edit a file, so the pull's strategy settles it, declared on the op: keep theirs, and yours is dropped; keep mine, and theirs is overwritten, its author taking a grudge against you; or keep both, which is resolving by hand and costs one more op. The hub shows the choice by what it does and prints the flag Git would use, which swaps under --rebase, as above. The one place the game is coarser than Git: a card is whole, so the losing side loses its commit, where Git loses only the lines that clashed.
