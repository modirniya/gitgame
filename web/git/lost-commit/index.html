I lost a commit

A commit you made is almost never gone. Every move of HEAD is written to the reflog, and a commit stays in the repository for weeks after nothing points at it. Three ways to lose one, and the way back from each.

A reset went too far

%CAPTURE:reset-too-far%

git reflog lists where HEAD has been, newest first: the reset at HEAD@{0}, the commit it took away at HEAD@{1}. git reset --hard HEAD@{1} moves the branch back there. Some shells want the braces quoted.

A branch was deleted

%CAPTURE:branch-deleted%

git branch -D prints the hash it deleted, which is one way back: git branch feature and that hash. The reflog is the other: the commit sits at HEAD@{1}, under the checkout that left the branch, and git branch feature HEAD@{1} makes the branch again, pointing at it.

A rebase dropped it

%CAPTURE:undo-rebase%

A rebase that settles every clash in the other side's favour (the conflict page's -X ours) can leave your commit with nothing to apply, and drop it. The reflog shows the rebase's start and finish, and Git keeps the branch's tip from before any rebase, merge or reset in ORIG_HEAD, so git reset --hard ORIG_HEAD is the whole undo. A pull after a forced push can drop a commit the same way.

Undo the last commit, keep the work

%CAPTURE:reset-soft%

The most asked Git question has the smallest answer. --soft moves the branch back one commit and leaves everything that commit had, staged and ready to commit again. --hard throws the changes away as well, which is the first case above.

What the reflog can't bring back

The reflog is per clone: it records your HEAD, not the remote's, so it has nothing on a commit that only ever existed on someone else's machine. It holds commits, not uncommitted work: changes that were never committed are gone after git reset --hard. And its entries expire, after 90 days, or 30 for a commit nothing reaches any more.
